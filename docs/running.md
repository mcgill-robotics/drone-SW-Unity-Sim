# Running the sim

Three processes: Unity, PX4 SITL, and whatever ROS 2 wants to listen. QGroundControl is optional.

## 1. Unity

Open the project in Unity 6.6 and load one of the scenes in `Assets/_Project/Scenes/`. Press
Play. The overlay in the top left says `PX4 SITL: waiting on TCP 4560` until PX4 connects.

| Scene | Vehicle | PX4 airframe (`PX4_SIM_MODEL`) |
|---|---|---|
| `Flight.unity` | Our quadplane: 6.5 kg, 16 inch props, placeholder aero | `gazebo-classic_standard_vtol` |
| `FlightX500.unity` | PX4's X500 quad, numbers from its Gazebo model | `none_iris` |

The X500 is what drone-2026 and drone-2027 tested against in Gazebo (`gz_x500`), so it's the
like-for-like replacement and the easiest vehicle to get hovering. Use the quadplane for
anything that needs the wing.

The project has Run In Background on, so play mode keeps stepping while you're in QGC or a
terminal. Without it Unity pauses when it loses focus, and PX4 logs `poll timeout` until you
click back into the editor.

The scenes are generated by `Assets/Editor/DroneSim/SceneBuilder.cs` (menu: Drone Sim > Build
Flight Scenes). Edit the builder, not the scenes, so the setup stays reviewable.

Headless compile and scene rebuild:

```bash
/Applications/Unity/Hub/Editor/6000.6.0f1/Unity.app/Contents/MacOS/Unity -batchmode -nographics -quit \
  -projectPath . -executeMethod DroneSim.Editor.SceneBuilder.Build -logFile build.log
```

Edit-mode tests (MAVLink encoding against pymavlink golden frames, frame conversions, geo math,
actuator scaling). Close the editor first; batchmode can't open a project that's already open.

```bash
/Applications/Unity/Hub/Editor/6000.6.0f1/Unity.app/Contents/MacOS/Unity -batchmode -nographics \
  -projectPath . -runTests -testPlatform EditMode -testResults results.xml -logFile test.log
```

In the editor: Window > General > Test Runner > EditMode.

## 2. PX4 SITL

PX4 connects to Unity as a TCP client on port 4560 and runs in lockstep with it.

Use the same PX4 release as the flight controller and drone-2027's `px4_msgs` (v1.17.0):

```bash
git clone --recursive -b v1.17.0 https://github.com/PX4/PX4-Autopilot.git
cd PX4-Autopilot
make px4_sitl                     # build only, launches nothing

# Flight.unity (quadplane)
PX4_SIM_MODEL=gazebo-classic_standard_vtol ./build/px4_sitl_default/bin/px4

# FlightX500.unity (quad)
PX4_SIM_MODEL=none_iris ./build/px4_sitl_default/bin/px4
```

On macOS, SITL builds with Apple's compiler, cmake and ninja from Homebrew, and PX4's Python
requirements in a venv; the ARM toolchain and Gazebo aren't needed. If Homebrew's protobuf is
installed, v1.17 tries to build its Gazebo messages against it and fails on C++17. We never use
them, so turn protobuf off:

```bash
python3 -m venv .venv && .venv/bin/pip install -r Tools/setup/requirements.txt
source .venv/bin/activate
ulimit -S -n 2048
make px4_sitl CMAKE_ARGS="-DCMAKE_DISABLE_FIND_PACKAGE_Protobuf=TRUE"
```

Both airframes start `simulator_mavlink`, which dials TCP 4560, and neither starts a simulator
of its own. PX4 has no `none_standard_vtol`, so the quadplane borrows the gazebo-classic
standard_vtol airframe (autostart 1040); Gazebo only starts if you use
`make px4_sitl gazebo-classic_standard_vtol`, so running the binary directly skips it.

Don't use the `gz_` airframes (`gz_x500`, `gz_standard_vtol`). They talk to Gazebo Harmonic over
its own transport instead of MAVLink, so they can't connect to Unity. `none_iris` is PX4's
quad-x airframe for external simulators: same motor order and spin directions as the X500, with
the Iris's slightly wider arm positions in its mixer, which PX4 flies without trouble. To match
the X500 exactly, set `CA_ROTOR0..3_PX/PY` to ±0.13 / ±0.22 (front) and ±0.20 (rear) in QGC.

If Unity runs on another machine, set `PX4_SIM_HOSTNAME=<unity host>` for PX4.

`PX4_HOME_LAT`, `PX4_HOME_LON` and `PX4_HOME_ALT` do nothing on the PX4 side here, because
PX4's home comes from the GPS that Unity sends. Set them in the environment Unity starts from
(or on `GeoOrigin` under `Managers`) to move the world. The default is the SUAS 2026 field.
The magnetic field on `GeoOrigin` doesn't follow; set it for the new site from NOAA's
magnetic field calculator, or PX4's EKF will complain about heading.

QGroundControl finds SITL automatically on UDP 14550. PX4 also starts the uXRCE-DDS client on
UDP 8888.

Unity blocks each physics step until PX4 answers. If PX4 stops answering for three steps, the
bridge stops waiting until the next controls arrive, and a dropped connection returns it to
`waiting on TCP 4560`.

## Smoke test

With Unity playing and PX4 connected, `tools/px4_smoke_test.py` arms, takes off, hovers for
10 s, lands and prints PX4's estimate once a second (`pip install pymavlink` first):

```bash
python3 tools/px4_smoke_test.py 5
```

First run on the X500 (2026-09-26): took off to 5.1 m, held altitude within 5 cm and position
within 10 cm with attitude inside 1 degree, landed at 0.7 m/s and disarmed itself. The quadplane
does the same.

On `Flight.unity`, `tools/px4_vtol_test.py` also flies the wing: climb to 40 m, forward
transition, 60 s of fixed-wing loiter, back-transition, land:

```bash
python3 tools/px4_vtol_test.py 40 60
```

First run (2026-09-26): forward transition in about 6 s, reaching 10 m/s; loitered at 10 to
14.6 m/s on an 80 m circle; back-transitioned and landed 7 m from home. It lost 8 m during the
transition and flew nose-high (12 to 14 degrees) at about 48% throttle. The placeholder wing is
too small or too draggy for 6.5 kg; real wing numbers should fix that.

If a run hangs with PX4's log stopped before `Simulator connected`, an old PX4 is still holding
its lock: `pkill -9 -f px4_sitl_default/bin/px4; rm -f /tmp/px4_lock-0 /tmp/px4-sock-0`.

## QGroundControl

QGC talks to PX4, not to Unity. PX4 SITL sends MAVLink to UDP 14550 on localhost, which is
where QGC listens, so QGC connects by itself once PX4 is up. The test scripts use 14540, so both
can be connected at once. To run QGC on another machine, set `MAV_0_BROADCAST 1` in PX4 or add
a UDP comm link in QGC.

First-run preferences: firmware PX4 Pro, vehicle VTOL (or no preference), metric units. SUAS
rules are in feet: the 150 to 400 ft band is 46 to 122 m.

`missions/vtol_flyaround.plan` is the same flight as `px4_vtol_test.py`, flown as a mission on
`Flight.unity`: VTOL takeoff to 50 m, transition heading north, a lap of about 1.2 km on the
wing around home, back-transition on the approach, land at home. To fly it:

1. Unity: play `Flight.unity`. Start PX4 with `gazebo-classic_standard_vtol`.
2. QGC: wait for "Ready To Fly" and the vehicle on the map at the SUAS field.
3. Plan view: File > Open, pick the plan, then Upload.
4. Fly view: slide "Start Mission". PX4 arms, takes off and flies it; it disarms after landing.

Change mode, Return, Land or Transition from the Fly view at any time. Without a joystick,
position mode needs Application Settings > General > Virtual Joystick. Flight logs (`.ulg`) land
in `PX4-Autopilot/build/px4_sitl_default/rootfs/log/`, and QGC can download them too.

## 3. ROS 2

The PX4 side of ROS 2. Use Micro-XRCE-DDS-Agent v2.4.2; v3.x doesn't work with PX4's client.

```bash
MicroXRCEAgent udp4 -p 8888
```

drone-2027's flight checks start the agent themselves with `--sitl`, so skip this when
running those.

The Unity side of ROS 2 (cameras, IMU, ground truth, /clock):

```bash
ros2 run ros_tcp_endpoint default_server_endpoint --ros-args -p ROS_IP:=0.0.0.0
```

Unity connects to the endpoint at 127.0.0.1:10000. Change the address on the `ROSConnection`
component under `Managers` if the endpoint runs elsewhere, for example in Docker.

## Running drone-2027's flight checks against Unity

drone-2027 (`feat/uxrce-dds-port`) talks to PX4 over uXRCE-DDS and doesn't care which
simulator is under PX4. Its `docs/sitl.md` says `make px4_sitl gz_x500`; with Unity, open
`FlightX500.unity`, start PX4 with `PX4_SIM_MODEL=none_iris` as above, then run its checks
unchanged:

```bash
ros2 run drone check_link --sitl
ros2 run drone check_telemetry --sitl --duration 10
ros2 run drone check_hover --sitl --api
```

- The checks fly in multicopter mode only. They never command a transition, so they also run
  on the quadplane, which hovers as a quad.
- `check_goto_gps` and `check_gps_movement` take coordinates near Zurich in their examples,
  and `check_lap` uses Montreal. Move Unity's origin to match (`PX4_HOME_LAT` etc. above) or
  pass coordinates near the Unity origin, or the vehicle will try to fly across an ocean.
- On a Mac, run PX4 SITL and Unity natively and the ROS 2 side in drone-2027's
  `docker/Dockerfile`, with UDP 8888 published.

## Keys

- `R` resets the vehicle to its start pose.
- `M` toggles manual keyboard flying, for when PX4 is not running. Shift/Ctrl collective, W/S pitch,
  A/D roll, Q/E yaw, Up/Down pusher, Space cuts. A small attitude hold keeps hover level.
- Right drag orbits the chase camera, scroll zooms.

The sim runs without ROS. The publishers retry the endpoint and log one error; nothing else
depends on it.

## Topics from Unity

| Topic | Type | Rate |
|---|---|---|
| /clock | rosgraph_msgs/Clock | 10 Hz |
| /sim/imu/data | sensor_msgs/Imu | 10 Hz default, set on the publisher |
| /sim/forward_cam/image_raw/compressed, /sim/forward_cam/camera_info | CompressedImage, CameraInfo | 10 Hz |
| /sim/down_cam/image_raw/compressed, /sim/down_cam/camera_info | CompressedImage, CameraInfo | 10 Hz |
| /sim/ground_truth/pose | geometry_msgs/PoseStamped | 50 Hz |
| /sim/ground_truth/twist | geometry_msgs/TwistStamped | 50 Hz |
| /sim/ground_truth/gps | sensor_msgs/NavSatFix | 50 Hz |

Subscribed: /simulation/reset (std_msgs/Bool).

## PX4 channel mapping on the quadplane

Taken from PX4's `1040_gazebo-classic_standard_vtol` airframe (`PWM_MAIN_FUNC1..8`). The same
table is in code as `StandardVtolChannels`, and a test pins it.

| Channel | Actuator | PX4 range | Notes |
|---|---|---|---|
| 0 | Lift rotor front-right | 0..1 | CCW (`CA_ROTOR0_KM` > 0) |
| 1 | Lift rotor rear-left | 0..1 | CCW |
| 2 | Lift rotor front-left | 0..1 | CW |
| 3 | Lift rotor rear-right | 0..1 | CW |
| 4 | Pusher | 0..1 | |
| 5 | Left aileron | -1..1 | positive rolls left (`CA_SV_CS0_TRQ_R` = -0.5) |
| 6 | Right aileron | -1..1 | positive rolls right (`CA_SV_CS1_TRQ_R` = +0.5) |
| 7 | Elevator | -1..1 | positive pitches nose up |

The airframe has no rudder. PX4's `pwm_out_sim` sends motors as 0..1 and servos as -1..1.

When the real airframe gets its own PX4 config, update `StandardVtolChannels` and this table
together. The X500 uses channels 0 to 3 in the same order and nothing else.
